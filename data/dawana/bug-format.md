# Bug Report Format

## Required sections

Bug markdown files use YAML frontmatter followed by a structured body. Frontmatter fields: status (e.g., draft), jira_key (null until filed), reported_at (null until reported), feature (module/feature slug, e.g., incident), priority (P1-P4), bug_type (Functional | Functional / Integration | Functional (Backend/API) | Functional — Intermittent / Flaky | UI/UX), title (a single descriptive sentence summarizing the defect). Body sections in order, separated by '---' horizontal rules: (1) an unlabeled Summary of 1-3 paragraphs describing what is broken, the context, and why it matters — including serialization/integration context (SGTIN/SSCC/Masar) when relevant; (2) optional 'Precondition:' section when specific pre-existing state is required (e.g., two incidents already created sharing an SGTIN); (3) 'Steps to Reproduce:' as a numbered list (Log in as [Role] -> Open [Module/Screen] -> [Action] -> [Action] -> Observe [what to look at]), which may reference concrete test data such as specific SGTIN URNs or account emails; (4) 'Expected Result:' one clear sentence describing what should happen; (5) 'Actual Result:' one clear sentence describing what actually happens; (6) 'Environment:' a bullet list with Device, OS, App Version, and Account/Role (and URL if web — not applicable for this mobile app); (7) 'Priority:' repeating the P1-P4 value with descriptive label; (8) 'Bug Type:' repeating the bug_type value.

## Severity / priority conventions

Priority scale (used both in frontmatter and body): P1 - Critical (e.g., cross-system Dawana/Masar desync causing silent data corruption, duplicate processing risk, broken traceability), P2 - High (e.g., invalid UI state persisting after a failed validation, breaking the product list), P3 - Medium, P4 - Low. Bug Type values: Functional (standard UI/logic defects), Functional / Integration (defects spanning Dawana <-> Masar synchronization), Functional (Backend/API) (API-level defects such as auth/validation errors), Functional — Intermittent / Flaky (non-deterministic reproduction), UI/UX (cosmetic/interaction issues not affecting data integrity). The most severe class of bug in this domain is silent data corruption / desynchronization between Dawana and Masar (e.g., a success message shown while the downstream trace transaction is missing, or an operation that appears to fail in Dawana but silently succeeds in Masar) — these are treated as Critical/P1 regardless of how minor the visible UI symptom looks, because they represent regulatory/traceability risk for a pharmaceutical supply chain.
