# Dawana — Platform & Domain Knowledge

## What this product is

Dawana is a mobile Android application (native app, tested as an installed APK) for a pharmaceutical / healthcare supply-chain and serialization ecosystem. It is used by pharmacies (Owners, Managers, Pharmacists) and by regulatory Inspectors to manage the full lifecycle of serialized pharmaceutical products: registration and onboarding of owners/pharmacies, receiving of stock (first-time entry and new-stock requests), dispensing/selling of serialized drug units to patients, handling of returns to distributors, reporting of incidents for problematic inventory (damaged, expired, incorrect quantity, discrepancies), and inspection/audit workflows. Dawana integrates with an external traceability/serialization system called Masar, which is the source of truth for SSCC hierarchy, SGTIN-level trace transactions, and product state transitions (e.g., marking items out-of-service after an accepted incident). The platform is built around GS1 serialization standards: GTIN (product identity), SGTIN (serialized/unique saleable unit = GTIN + serial number), SSCC (Serial Shipping Container Code, representing a logistics unit such as a carton/case/pallet), batch, and expiry. A single invoice/shipment can contain multiple SSCCs and multiple products, and receiving can happen either by scanning individual SGTINs or by receiving whole SSCCs (aggregation/disaggregation). Because the domain is pharmaceutical, the platform is safety- and compliance-critical: every inventory mutation is expected to produce a corresponding transaction/trace entry, and Dawana's UI state must remain synchronized with backend stock state and with Masar's trace state. The most dangerous class of defect in this domain is not a UI bug but silent data corruption — e.g., Dawana showing a success message ("Dispense completed") while Masar shows the SSCC quantity decreasing with no corresponding trace transaction, indicating a synchronization or transaction-persistence failure between the two systems. Testing strategy must therefore always validate not just the UI result but also the backend response, inventory state, SSCC state, the Masar trace transaction, and rollback behavior after any failure — never trust a success toast or frontend state alone.

## User roles

- Owner (Pharmacy Owner) — Registers as an Owner and registers a pharmacy; uploads owner/pharmacy documents; pharmacy has a Pending/Approved status. Can log in as Pharmacy > Pharmacy Owner. Can request changes to Manager/Pharmacy data (Request Change flow), perform Dispense (Owner flow), view pharmacy list and details, request a new pharmacy, view owner reports, inspection history, notifications, and manage own profile. Can submit Incident Form (Owner variant, OWN_FR_15). Is blocked from accessing Manager, Pharmacist, and Inspector modules (role isolation is enforced and tested).
- Manager (Pharmacy Manager) — Registers/logs in as Pharmacy > Pharmacy Manager. Performs First-Time Setup (adding initial quantities/stock), Dispense (Manager flow), views Transactions History and Stock Quantity, requests Renewal Dispense Letter, views the Manager Home Dashboard, manages expiry dates, submits the Incident Form (primary role for incident reporting, MGR_FR_29 — scans/selects a product, selects an incident reason such as Damaged/Expired, the system validates quantity/batch/stock/serialized units, and the user confirms the incident which triggers backend inventory changes), adds new Pharmacists, creates New Stock Requests, handles Returned Products Requests, views Laws & Regulations, Manager Reports, and manages own profile and leave. A resigned/removed Manager account is blocked from login with a clear message (a pharmacy can only have one active manager at a time in the system). Is blocked from Owner/Pharmacist/Inspector modules.
- Pharmacist — Logs in as Pharmacy > Pharmacist, then selects a pharmacy (Pharmacy Selection). Performs Dispense (Pharmacist flow), including selling using an agent in Strip mode or Pack mode (dispensing serialized packs, updating SSCC contents, deducting inventory, registering a trace transaction). Views Transaction History, processes Return Items, performs Stock Lookup, views Pharmacist Reports/Notifications, and manages own profile. Is blocked from Owner/Manager/Inspector modules.
- Inspector — Regulatory/auditor role, logs in via a separate Inspector role-selection path (no Pharmacy/Owner/Manager/Pharmacist sub-role selection). Searches for pharmacies, starts and submits inspections, performs inventory verification and transaction audits, documents offenses, reviews first-time product entries, reviews expiry-warning reports, investigates incidents, and — critically — accepts or rejects pending incidents raised by Pharmacy Managers/Owners (Incident module: incidents sit in "Wait to Accept or Reject" status until an Inspector acts on them; accepting triggers a Masar operation that marks items out-of-service). Views Inspector Dashboard, Inspector Reports, and manages own profile. Is blocked from all Pharmacy-role modules. Multiple roles can exist on one account/device (e.g., Owner + Pharmacist), with the app switching context correctly based on the role selected at each login.

## Core concepts & entities

- GTIN (Global Trade Item Number) — Represents the identity of a pharmaceutical product (not unit-specific).
- SGTIN (Serialized GTIN) — GTIN + unique serial number; identifies a single saleable/serialized pharmaceutical pack. Format example observed: urn:epc:id:sgtin:<company>.<item>.<serial> (e.g., urn:epc:id:sgtin:08401496.05208.TC07XANAX0002). SGTINs must be unique and are the atomic unit of traceability.
- SSCC (Serial Shipping Container Code) — Identifies an entire logistics unit (carton/case/pallet) that can contain multiple SGTINs/products. An invoice may reference multiple SSCCs; receiving can be done per-SGTIN or per whole SSCC (aggregation/disaggregation), and parent-child SSCC hierarchy must remain correct after any product removal.
- Batch — Production lot identifier for a pharmaceutical product; used together with expiry and stock validation.
- Invoice / Bill — A receiving document with fields such as branch_code, pharmacy_code, bill_number, total_price, and a products[] list (each product having name, batch, expiry, quantity, and serialized identifiers).
- Incident — A record raised (typically by a Pharmacy Manager or Owner) against one or more serialized products for a reason such as Damaged, Expired, incorrect quantity, or inventory discrepancy. Moves through statuses including "Wait to Accept or Reject" -> "Pending Masar" -> Accepted/Rejected. Acceptance is performed by an Inspector and triggers a downstream Masar operation.
- Transaction / Trace entry — A record in Masar of a serialized-product movement or state change (e.g., dispense, incident acceptance). Every inventory mutation in Dawana is expected to generate a corresponding trace transaction in Masar; a missing trace transaction after a successful-looking operation is considered a critical defect.
- Masar — External/integrated traceability system responsible for serialization traceability, SSCC hierarchy tracking, product state transitions, and transaction/trace history. Dawana's UI/backend state must stay synchronized with Masar's state.
- Dispense / Sell Using Agent — The workflow of selling/removing pharmaceutical units to a patient, with Strip mode and Pack mode variants; deducts inventory, updates SSCC contents, and should register a Masar trace transaction.
- Return (Return to Distributor / Return Item) — Workflow for returning previously received or dispensed serialized products, handled at both Manager (Returned Products Requests) and Pharmacist (Return Item) levels.
- New Stock Request — Manager-level workflow for requesting/receiving new stock into the pharmacy's inventory.

## Key workflows

Authentication/onboarding: A user launches the app and first chooses a top-level role — Pharmacy or Inspector. If Pharmacy is chosen, the user must then choose a sub-role (Pharmacy Owner, Pharmacy Manager, or Pharmacist) before tapping 'Get Started', which navigates to a Login screen; Inspector skips the sub-role step. Login requires Email + Password (mandatory validation on both), supports password show/hide, a 'Forgot your password?' link into the Forget Password flow, and is rate-limited after repeated failed attempts. The selected role must match the account's actual role on the backend — a mismatch is blocked with a role-specific 'not authorized' message rather than a generic error. After login the user lands on a role-specific dashboard/home; logout invalidates back-button access to any previously-opened protected screen. Owner registration/pharmacy registration: Owner registers, registers a pharmacy, and uploads owner/pharmacy documents; the pharmacy then has a Pending/Approved status gating further access. Owners can also request changes to Manager or Pharmacy data via a Request Change flow. Manager first-time setup: after being onboarded, a Manager performs a First-Time Entry to add initial stock quantities before other Manager features (dispense, incidents, reports) become meaningful. New Stock / Receiving: stock can be received by scanning individual SGTINs (serialized packs) or by receiving a whole SSCC (carton/case), supporting hierarchical/aggregated receiving; an invoice can contain multiple SSCCs and multiple products. Dispense (Owner/Manager/Pharmacist flows): the selling workflow supports Strip mode and Pack mode when 'selling using an agent'; the flow deducts inventory, updates SSCC contents, and should register a trace transaction in Masar. A known critical defect pattern is the UI showing a dispense-success message while Masar shows the SSCC quantity decreasing, the product disappearing from the SSCC, and no corresponding trace/transaction appearing — i.e., a UI-success/backend-failure desync. Incident workflow: a Manager (or Owner) opens the Incident module, selects or searches for a product, selects an incident reason (e.g., Damaged, Expired), scans the product/carton, the system is expected to validate quantity against available stock, batch, and serialized-unit correctness, and the user then confirms the incident, which should trigger backend inventory changes and place the incident into 'Wait to Accept or Reject' status. Two known high-priority defects exist here: (1) if a product fails barcode-scan validation, the system correctly shows a validation error but incorrectly still adds the product to the incident's product list/cart, leaving invalid, non-scanned entries in the UI that keep failing on resubmission; (2) stock-quantity validation (e.g., max quantity 30, user enters 31) may not block early enough on the frontend. An Inspector then reviews pending incidents and taps Accept or Reject; accepting triggers a 'Pending Masar' status and a downstream Masar operation that should mark the affected serialized items out-of-service. A known critical cross-system defect: when two active incidents share an SGTIN, accepting the second (after the first is already accepted) can silently fail on Dawana's side — the status briefly shows 'Pending Masar' then reverts to 'Wait to Accept or Reject' with no error shown, while Masar nonetheless processes and commits the acceptance for all items including the duplicate SGTIN, producing a Dawana/Masar desync and a duplicate-processing risk. Return workflows: Pharmacists can return individual items; Managers handle returned-product requests at the pharmacy level. Inspection workflow: an Inspector searches for a pharmacy, starts an inspection, verifies inventory, audits transactions, documents offenses, and submits the inspection; Inspectors also review first-time product entries, expiry-warning reports, and investigate incidents (including accept/reject as above). Cross-cutting testing mindset for every workflow: always verify (1) UI result, (2) backend response, (3) inventory state, (4) SSCC state, (5) the Masar trace transaction, (6) Dawana<->Masar synchronization, and (7) rollback behavior after a failure — a success toast or frontend state alone is never sufficient evidence that an operation truly completed.

## Glossary

- GTIN — Global Trade Item Number — represents pharmaceutical product identity (not unit-specific).
- SGTIN — Serialized GTIN — GTIN + serial number; identifies a single saleable/serialized pharmaceutical unit.
- SSCC — Serial Shipping Container Code — identifies an entire logistics unit (carton/case/pallet); can contain multiple SGTINs/products.
- Trace / Trace transaction — A transaction history entry in Masar recording movement or state change of a serialized product.
- Dispense — Selling / removing pharmaceutical units from stock to a patient.
- Incident — A reported problematic-inventory workflow item (damaged, expired, incorrect quantity, discrepancy) that must be accepted or rejected by an Inspector.
- Batch — A production lot identifier for a pharmaceutical product.
- Agent Selling / Sell Using Agent — An assisted selling/dispense workflow supporting Strip mode and Pack mode.
- Masar — External integrated traceability/serialization system that Dawana synchronizes inventory and trace state with.
- Aggregation/Disaggregation — The process of grouping serialized items into an SSCC (aggregation) or breaking an SSCC apart into its constituent items (disaggregation).
- Wait to Accept or Reject — Incident status while pending Inspector decision.
- Pending Masar — Transient incident status while the Masar-side operation for an accepted incident is being processed.
