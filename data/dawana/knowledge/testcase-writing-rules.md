# Test-Case Writing Rules

## ID scheme

3-part TestCase IDs, always 3-digit zero-padded and sequential per feature file (resets to _001 for each new feature module, never skips numbers). Cross-role/general features use a fixed prefix: LGN_{###} (Login), DSP_{###} (Dispense), REG_{###} (Registration), FRPW_{###} (Forget Password). Role-specific features use ROLE_FEATURE_{###} (e.g., MGR_FTE_{###} Manager First-Time Entry, MGR_NST_{###} Manager New Stock, MGR_INC_{###} Manager Incident Form, OWN_RCH_{###} Owner Request Change, PHR_INC_{###} Pharmacist Incident Reporting). When one file covers both Manager and Pharmacist variants of the same feature, use the primary role's prefix. Each test case also carries a Feature ID column referencing requirements/FRs.md (e.g., GEN_FR_00 for general/cross-role tests, or the specific role Feature ID such as MGR_FR_29; if a test spans multiple features, list all Feature IDs space-separated).

## Required fields / table format

Every test-case file begins with a single H1 heading naming the module, followed by one markdown table with this exact 13-column, case-sensitive order (preserve the source's own typos verbatim, e.g. 'Enviroment' and trailing space in 'Type '): Feature ID | TestCase ID | Tester | Validity | Test Cases Title / Objective | Environment | Pre-condition | Test Data | Steps | Expected Results | Status | Attachment | Type. Status column values: Pass (executed and passed), Fail (executed and failed — MUST have a bug ID in Attachment), Blocked/Skipped (cannot test yet: pending backend, TBD rule, environment unavailable, or confirmed future work), Under Testing (currently being actively tested). Attachment column: empty when Status is Pass/Blocked-Skipped/Under Testing; a bug ID formatted DW-{###} (e.g., DW-320) when Status is Fail, multiple bugs space-separated (e.g., 'DW-320 DW-321'); a Fail status with no Attachment is treated as an authoring error. Type column is always 'Functional'.

## Style rules

Pre-condition: all steps written on a SINGLE table-cell line as a numbered list (no line breaks), following fixed role-based templates. Manager template: '1. Install Dawana App -> Test APK 2. Access to Wifi or Mobile data (prefered 4G or above) 3. Launch the app 4. Select Pharmacy Role 5. Select Pharmacy Manager 6. Tap Get Started button 7. Login with a Pharmacy Manager account 8. Open {Module Name} module'. Owner/Pharmacist templates are the same shape but end with '{Navigation to screen} ... User is on {Screen Name} screen'. Inspector template omits the Pharmacy sub-role step ('4. Select Inspector Role 5. Tap Get Started button 6. Login with a valid Inspector account ...'). Preserve exact wording quirks: 'Wifi' (not 'WiFi'), 'prefered' (not 'preferred'), 'Test APK' (no URL required in newer entries though older examples include a Google Drive APK link), always end with 'User is on {Screen Name} screen' or 'Open {Module} module'; add specific pre-existing state when relevant (e.g., 'At least one incident exists', 'Manager account; pharmacy has no stock on system'); for role-isolation negative tests the precondition intentionally describes use of the WRONG role. Test Data: 'Not Applicable' when nothing specific is needed (never 'N/A'); otherwise 'FieldName: value', multiple values semicolon-separated (e.g., 'Email: existing email; Password: Aa1!aaaa'). Standard test-data values used repeatedly: valid password Aa1!aaaa; too-short (7 chars) Aa1!aaa; no uppercase aa1!aaaa; no lowercase AA1!AAAA; no number Aa!aaaaa; no special char Aa1aaaaa; has spaces 'Aa1! aaA'; zero quantity 0; negative quantity -5; decimal quantity 2.5; scientific notation 1e3; SQL injection "' OR 1=1 --"; XSS injection '<script>alert(1)</script>'; emoji in field '123😀'; whitespace-only '   '. Steps column: numbered list on a single line, one atomic action per step, using verbs like Tap, Enter, Select, Upload, Observe, Scan, Open, Navigate, Disable, Enable, Leave, Wait, Rotate, Paste, Copy, Scroll, Repeat, Confirm, Pull to refresh; 'Observe {element/behavior}' for passive checks, 'Leave {field} empty' for empty-field tests; max ~10 steps per case (split into another test case if more are needed); 'Repeat steps X-Y' is acceptable for repetition; never repeat pre-condition steps inside the Steps column; steps must flow logically from where the pre-condition leaves off. Expected Results: a single declarative present-tense sentence, subject is 'System', the screen name, the actor, or 'Validation message' — never modal verbs ('should'/'will'/'would'/'shall'); be specific about the exact behavior; for unclear business rules append '(as per business rules)' or '(TBD with PO)'. Template patterns: screen opens -> '{Screen Name} is displayed successfully.'; back navigation -> 'User returns to {previous screen} without crash.'; successful save -> '{Entity} is saved successfully and {downstream effect}.'; mandatory field empty -> 'Mandatory validation message is displayed and {action} is not submitted.'; invalid format -> '{Field} format validation message is displayed and {action} is not submitted.'; role blocked -> '{Module} module is not accessible for {Role} role.'; network error -> 'System shows a clear network error and {stays on screen / allows retry}.'; duplicate blocked -> 'System prevents duplicate {entity} or merges according to business rules with clear behavior.'; loading state -> 'Loading indicator is shown until {operation} completes.'; quantity exceeded -> 'System blocks submission and shows quantity limit message.'

## Priority scale

Test-case files themselves do not carry a numeric/lettered priority column (priority lives at the Feature Requirement level in requirements/FRs.md, using P1 (highest/critical) through P4 (lowest) — e.g., P1 for Login/Registration/core Dispense, P2 for Incident Form/Dashboard/Expiry management, P3 for Returned Products/Leave Management/Request New Pharmacy, P4 for Reports/Profile/Notifications). Bug reports use the same P1–P4 scale with descriptive labels: P1 - Critical, P2 - High, P3 - Medium, P4 - Low. Validity column on test cases is a binary classification (Positive/Negative), not a priority.
